# 设计决策

每条红线背后都是一次踩过的坑。这里记录"为什么"，好让以后能判断一条规则还要不要。要推翻某条决策，先改这里，再改代码。

## 0. 产品与流程的分界

第 1–9 条是产品设计；第 10–11 条是维护流程。产品约束保护用户的故事和数据，不能为了省事放松；流程约束服务于效率，发现它在拖慢工作而没有挡住真实事故时，应该改掉。

## 1. 单作者，director 固定 3/2/2

**背景**：早期让多个模型分段写、或让专家直接改稿，人物声音会漂，前后文矛盾，出了问题也说不清是谁写的。
**决定**：只有主 Agent 写正文。director 的专家只交报告，同阶段互不可见，由主作者决定采纳。阶段数固定，不按"日常/关键回合"变化。
**代价**：director 慢、贵；需要快就用 direct。

## 2. 会话树是唯一事实

**背景**：摘要、账本、记忆一旦被当成事实，错误会自我强化；分支之间的派生状态也会互相污染。
**决定**：只有 `rpNarrative` 是事实。其它全是派生物，绑定 session、卡和合法祖先 source，可以丢弃重建。
**代价**：每个派生领域都要做来源校验和收据。

## 3. 原稿先交付，后台再整理

**背景**：正文写完后还要等账本、世界、数据库、MVU 全跑完才上屏，任何一个后台环节失败都会拖住或"撤回"一篇写好的正文。
**决定**：完整原稿落盘就上屏。后台并发计算、串行落树；失败留 pending，下一拍按收据补，已完成的不重复。
**代价**：派生面板可能比正文晚一点更新；共享写锁要保持到后台结束，下一条输入要排队。

## 4. 不设作者格式门槛

**背景**：要求作者必须交出某种面板、选项或状态栏才算成功，导致反复重试、重写好稿，还会让模型为了过格式检查牺牲正文。
**决定**：正文原样保存交付。卡要求但作者没交的附属格式，由独立后台补交，结果存专用条目，不改原稿，不进事实；其中作者漏交的变量更新块交给 MVU，否则卡的事件条件永远成立、每拍重复补。
**代价**：附属格式偶尔会晚到或缺失。

## 5. 不靠堆提示词修 bug

**背景**：每修一个问题就往 system prompt 或回执里加一句提醒，送模文本越来越长、越来越矛盾，模型越来越难同时遵守，旧问题换个样子又回来。
**决定**：修复优先删句子，或改成数据/工具通道。注入通道是封闭集合，每个通道只有一个负责人。不枚举卡作者起的名字来猜意图。
**代价**：有些问题要动机制才能修，不能靠一句话快速止血。

## 6. 原插件不 fork

**背景**：fork 后每次上游更新都要手工合并，改过的地方说不清，还会继承许可问题。
**决定**：原插件按固定来源、原字节运行，梨园只写宿主适配。上游出现新 API 时拒绝候选版本，补宿主而不是改原件。
**代价**：宿主要模拟足够多的酒馆环境；有些原插件行为只能做到"兼容"，不能完全等价。

## 7. 数据库启用时，文学导演并入原生召回

**背景**：原数据库自带召回/剧情推进任务，梨园的文学导演也要读相同资料。分开调用会重复花钱、重复读上下文。
**决定**：数据库启用时，导演候选由同一次原生召回请求产出，模型由"记忆召回 / 剧情推进 / 文学导演"统一入口管理。候选缺失就降级，不再发第二个请求。数据库关闭（默认）时仍走独立导演。

## 8. 模型岗位独立，不借用主演

**背景**：插件岗位缺配置时悄悄用主演模型，会烧主演的额度、走错网络，用户也不知道到底调用了什么。
**决定**：每个岗位独立解析。插件岗位必须显式配置，缺了就明确失败。文档不写推荐模型：用哪个模型取决于手头有哪些 API，过去的探针结果没有参考价值。

## 9. 隐私：GitHub 只放源码

**背景**：工作目录里同时有源码和私人数据（角色卡、Key、会话、记忆、插件缓存）。
**决定**：公开范围用白名单（`scripts/public-repository-policy.mjs`）。推送用 `npm run git:public` 导出到仓库外的候选，再加 hook 和 CI 扫描。私人数据原路径保留，不迁移、不上传。

## 10. 防御按可逆性分级，流程保持轻量

**背景**：曾经每出一次问题就加一道检查，从来不删。结果很小的修改也要配一批一次性脚本、冻结进程号和哈希的发布前置断言、多轮真实模型续跑；上线卡在供应商超时上，而产品本身早就按收据容忍后台 pending（第 3 条）。验收脚本误判又引出"原失败 + 纠正证据"的双轨记录。检查越多越脆：换个版本号要改好几处，合法的启动期配置重写也会被当成异常。
**决定**：只对不可逆的事设硬门禁：隐私泄露、改动生产故事/记忆/私人配置、打断正在进行的生成。可撤回的事（改代码、部署）用一次 `verify` + 冒烟 + 保留旧 release 快速回退兜底。真实模型和供应商可用性属于外部不确定，只观察记录，不当上线条件。出问题修根因，不叠流程。细则见 [AGENTS 防御分级](../AGENTS.md#防御分级)、[TESTING 什么时候跑什么](../TESTING.md#什么时候跑什么)、[运维 部署](../deploy/VPS-OPERATIONS.md#部署)。

## 11. 文档写机制，不写防御清单

**背景**：旧文档有约 200 条编号规则，大量"不……不……不……"的否定句和实现细节，同一约束在四五篇里各写一遍，每篇结尾再列一份会过时的测试清单。读者要花很久才知道系统怎么运作，改代码时也很难判断哪条还有效。
**决定**：每篇先讲机制，再列真正会被违反的约束；一件事只写在一处，其它地方链过去；具体数值和文件清单以代码为准，只写出处。去掉规则编号，跨篇引用链到章节标题。
**代价**：评审时不能再用"违反 P23"这类短引用，要链到章节。
**代价**：偶尔会把有问题的版本推上线，需要回退一次；真实模型偶发问题可能在生产里才第一次被看到。相比每次发布耗掉一整天，这个代价更小。
